# Mapping — Phase 4

For every invariant from `invariants.md` and every guarantee from
`guarantees.md`, this document records:

- The Commanded / reference-adapter mechanism.
- The proposed `instructed` realisation (schema, stored procedure,
  SDK convention, or "dropped").
- Whether the resulting guarantee is **tighter**, **equivalent**, or
  **looser** than Commanded's, and why that is acceptable.

`instructed`'s realisation is Postgres-native: schema constraints,
stored procedures, careful lock ordering, and a thin SDK loop. The
worklist is the Part G classification from `guarantees.md` (I /
B / C). Items marked **(I)** must be reproduced semantically; **(B)**
items disappear with the BEAM mechanism unless the semantics they
backed are also (I) somewhere; **(C)** items are evaluated on
ergonomic merit.

This is a living document. It is being written in passes, not in one
shot, so the reader can review the reasoning incrementally.

## Pass 1 — Append, Read, Aggregate execution

### Part B — Append (`append_to_stream`)

#### INV-APPEND-001 — Unique `event_id` per event

- **Commanded:** UUID v4 generated by the dispatcher; stored as
  `events.event_id` with a `UNIQUE` constraint.
- **`instructed`:** identical. `events.event_id UUID PRIMARY KEY` (or
  `UNIQUE NOT NULL`). The SDK generates the UUID; the stored
  procedure rejects collisions via the unique constraint, surfaced as
  `:duplicate_event` (see INV-APPEND-030).
- **Verdict:** **equivalent**.

#### INV-APPEND-002 — Contiguous per-stream `stream_version` starting at 1

- **Commanded / reference adapter:** unique constraint on
  `stream_events (stream_id, stream_version)`; `append_to_stream`
  computes `next = max(stream_version) + 1` inside its transaction and
  inserts. Concurrent appenders that compute the same `next` collide
  on the unique constraint.
- **`instructed`:** same structure. The events table carries
  `(stream_id, stream_version)` with a unique constraint; the
  `append_to_stream` stored procedure computes the next version under
  whatever serialisation point we choose for the stream (see
  INV-APPEND-022 below). Gap-freedom falls out of "compute from current
  max, with appends serialised per stream".
- **Verdict:** **equivalent**.

#### INV-APPEND-003 — Globally gapless, monotonic `event_number`

- **Commanded / reference adapter:** assigned via `$all`-as-stream:
  there is a real `streams` row for `$all`, and every append takes
  its row-level lock to obtain `next_event_number = $all.version + 1`,
  then links every event into `$all` via `stream_events` with
  contiguous numbers. Lock ordering is `streams[target] →
  streams[$all] → events → stream_events`.
- **`instructed`:** **mechanism is OQ-0001**. The candidates are
  (1) `$all`-as-stream like the reference, (2) a Postgres sequence
  (loses gap-freedom; needs invariant revision), or (3) `SERIALIZABLE`
  + `MAX() + 1`. The default assumption pending OQ-0001 is option 1,
  because it most directly preserves the invariant as written and
  matches the reference adapter's lock ordering.
- **Verdict:** **equivalent** under option 1 (the current default);
  **looser** under option 2 (would require weakening INV-APPEND-003
  to "monotone, not gapless"); **equivalent but lower throughput**
  under option 3.

#### INV-APPEND-004 — Contiguity within a single multi-event append

- **Commanded:** the entire multi-event insert is a single SQL
  statement (or a single transaction) inside `append_to_stream`. No
  other writer can interleave because the per-stream and `$all`
  locks are held for the whole call.
- **`instructed`:** same. `append_to_stream` is a stored procedure
  that runs in a single transaction, acquires the per-stream
  serialisation point first, then the global serialisation point
  (whatever OQ-0001 picks), inserts all N events with contiguous
  `stream_version` and `event_number`, and commits.
- **Verdict:** **equivalent**.

#### INV-APPEND-005 — `created_at` is UTC, non-decreasing modulo clock skew

- **Commanded:** `NOW()` inside the insert. No monotonicity
  enforcement.
- **`instructed`:** same. `created_at TIMESTAMPTZ NOT NULL DEFAULT
  now()`. We do not enforce monotonicity beyond what the server
  clock provides.
- **Verdict:** **equivalent**.

#### INV-APPEND-006, INV-APPEND-007 — Atomicity of multi-event append

- **Commanded:** one transaction per `append_to_stream` call;
  trigger raises on `UPDATE`/`DELETE`.
- **`instructed`:** identical. The stored procedure is the
  transaction boundary. Triggers (see INV-APPEND-040) prevent
  post-commit tampering.
- **Verdict:** **equivalent**.

#### INV-APPEND-010..014 — Expected-version semantics

Same SDK-facing contract; only the enforcement mechanism varies.

- **Commanded / reference adapter:** the unique constraint on
  `(stream_id, stream_version)` (INV-APPEND-022) does the work.
  Existence checks for `:no_stream` / `:stream_exists` are explicit
  reads of `streams` early in the procedure.
- **`instructed`:** stored procedure `append_to_stream` accepts the
  same union (`:any_version`, `:no_stream`, `:stream_exists`,
  non-negative integer) as a SQL-friendly encoding (e.g. a `text`
  column plus a nullable integer; details deferred to Phase 7).
  Inside the procedure:
  - `:any_version` → upsert stream row, append.
  - `:no_stream` → require `streams[stream_uuid]` not to exist;
    raise `stream_exists` SQLSTATE otherwise.
  - `:stream_exists` → require it to exist; raise `stream_not_found`
    otherwise.
  - integer V → require current version = V; raise
    `wrong_expected_version` otherwise.
  Error SQLSTATEs map 1:1 to the closed error set; the SDK
  translates them to the language-native error type.
- **Verdict:** **equivalent**. The SDK-visible error set is
  identical.

#### INV-APPEND-020, INV-APPEND-021 — Concurrent appends

- **Commanded:** under integer expected_version, the unique
  constraint guarantees at most one winner. Under `:any_version`,
  the `$all` row lock serialises all concurrent appenders globally;
  per-stream order falls out of taking the per-stream lock first.
- **`instructed`:** same. INV-APPEND-020 is enforced by whatever
  mechanism INV-APPEND-022 picks. INV-APPEND-021's contiguity
  guarantee depends on the choice in OQ-0001.
- **Verdict:** **equivalent** (subject to OQ-0001).

#### INV-APPEND-022 — Mechanism of expected-version enforcement *[reference-only]*

- **Commanded / reference adapter:** unique constraint on
  `stream_events (stream_id, stream_version)`. The "loser" of a
  concurrent insert gets `unique_violation` (SQLSTATE 23505), which
  the adapter translates to `:wrong_expected_version`.
- **`instructed`:** **same mechanism**. We adopt the unique
  constraint approach explicitly: it composes with multi-event
  inserts (one constraint check per row, all in one statement) and
  it is the cheapest way to enforce contiguity without a per-stream
  lock held across user code. Alternative considered:
  predicated update (`UPDATE streams SET version = version + N
  WHERE stream_uuid = ? AND version = ?`). Both work; we prefer
  the unique constraint because it generalises to "any append that
  computes the wrong next version fails", not just to integer
  expected_version.
- **Verdict:** **equivalent** by deliberate adoption of the same
  mechanism. (We considered this an open question and resolved it
  inline; no OQ entry created.)

#### INV-APPEND-030 — Re-append of existing `event_id`

- **Commanded:** `unique_violation` on `events.event_id` →
  `:duplicate_event`.
- **`instructed`:** same. The SDK never relies on this — it always
  generates fresh UUIDs — but the error is surfaced for diagnostic
  value.
- **Verdict:** **equivalent**.

#### INV-APPEND-040, INV-APPEND-041 — Immutability and deletion

- **Commanded / reference adapter:** triggers raise on `UPDATE` /
  `DELETE` against `events` and `stream_events`. A gated hard-delete
  bypasses the trigger.
- **`instructed`:** trigger that raises on `UPDATE` and `DELETE` on
  the events table. **No hard-delete in v1** (per
  INV-DELETE-001 below). Operators who need to scrub data must do
  so out-of-band and own the consequences.
- **Verdict:** **tighter**. We drop the hard-delete escape hatch.
  This is a deliberate non-goal candidate for Phase 5.

### Part C — Read (`stream_forward`)

#### INV-READ-001 — `:stream_not_found` for never-appended stream

- **Commanded:** check `streams` row presence before streaming.
- **`instructed`:** stored procedure `read_stream` does the same:
  early `EXISTS` check on `streams`, raise / return
  `:stream_not_found` if missing.
- **Verdict:** **equivalent**.

#### INV-READ-002..004 — Order, exhaustiveness, inclusive start

- **Commanded:** `SELECT ... WHERE stream_id = ? AND stream_version
  >= ? ORDER BY stream_version LIMIT batch`. SDK pages until
  exhausted.
- **`instructed`:** identical. The stored procedure (or a direct
  prepared statement; deferred to Phase 7) returns a cursor or a
  paged result set. SDK loops until empty.
- **Verdict:** **equivalent**.

#### INV-READ-005..008 — `:all` semantics

- **Commanded / reference adapter:** `:all` is `stream_id = 0` in
  the `stream_events` join; the row carries `original_stream_id`
  and `original_stream_version` so the projection back to a
  `RecordedEvent` shows the *original* stream identity.
- **`instructed`:** the choice between (a) `$all` as a real join
  table (reference-style) and (b) `$all` as a view over
  `events ORDER BY event_number` is bound up with OQ-0001. Under
  option 1 of OQ-0001 we naturally get (a); under option 2 we'd
  get (b). The SDK-visible behaviour is the same either way: the
  `RecordedEvent` projection carries the original stream identity
  in `stream_id`/`stream_version` and the global position in
  `event_number`.
- **Verdict:** **equivalent**.

#### INV-READ-020 — Reader/append concurrency

- **Commanded:** snapshot isolation gives consistent reads;
  pagination may or may not lazily pick up newer appends.
- **`instructed`:** same — Postgres' MVCC gives us this for free.
  The SDK MUST NOT rely on "page N+1 sees events appended after
  page N's snapshot" because the contract doesn't promise it.
- **Verdict:** **equivalent**.

### Part F — Cross-cutting (Streams, Meta, Delete, Links)

#### INV-META-001 — Causation/correlation persisted and echoed

- **Commanded:** stored as columns on `events`.
- **`instructed`:** same. `events.causation_id UUID`,
  `events.correlation_id UUID`, both nullable.
- **Verdict:** **equivalent**.

#### INV-META-010, INV-META-011 — `event_type` opaque; data/metadata round-trip

- **Commanded:** `event_type TEXT`, `data BYTEA`, `metadata BYTEA`
  (serializer is application-chosen).
- **`instructed`:** **`data JSONB`, `metadata JSONB`**. We pin
  JSONB as the only on-disk encoding for v1 because (a) it lets
  the store be queried directly (useful for habitat-style admin
  UIs in future), (b) it avoids the serializer-coupling problem
  that bytea has, and (c) Postgres handles compression. The SDK is
  responsible for `serialise(payload) -> jsonb` and the inverse.
  `event_type TEXT NOT NULL` echoes the caller's string.
- **Verdict:** **tighter, with a cost**. We give up the ability to
  store opaque term-binary or Avro blobs directly. Applications
  that need binary payloads must base64-into-JSONB or wait for a
  later `_bin` column. Recording this as a deliberate constraint
  for Phase 5 / non-goals.

#### INV-STREAM-001, INV-STREAM-003 — `stream_uuid` as identity; `$all` reserved

- **Commanded:** `streams.stream_uuid TEXT UNIQUE NOT NULL`; the
  reference adapter uses `$all` as the literal name of the global
  stream and forbids it as a user identifier by convention.
- **`instructed`:** same. `streams.stream_uuid TEXT PRIMARY KEY`
  with a `CHECK (stream_uuid <> '$all')` so collisions are
  schema-enforced rather than convention-enforced.
- **Verdict:** **tighter** (schema-level enforcement of the
  reserved name).

#### INV-STREAM-002 — Internal numeric `stream_id` *[reference-only]*

- **Commanded:** `BIGSERIAL stream_id` joins everything internally.
- **`instructed`:** same shape. `streams.stream_id BIGSERIAL
  PRIMARY KEY`, `stream_uuid TEXT UNIQUE`. All other tables join
  on `stream_id`. Pure implementation detail; not visible across
  the SDK contract.
- **Verdict:** **equivalent**.

#### INV-LINK-001 — User-facing event linking *[reference-only]*

- **Commanded:** not exposed via the adapter behaviour, only used
  internally to populate `$all`.
- **`instructed`:** **dropped**. We do not expose linking.
  Whether `$all` is itself a link table or a view is OQ-0001 work.
- **Verdict:** **looser by elimination** (no user-facing linking),
  but Commanded didn't expose it either, so no application breaks.

#### INV-DELETE-001 — Gated hard-delete

- **Commanded / reference adapter:** offers it behind a session
  setting.
- **`instructed`:** **dropped from v1.** See INV-APPEND-040/041
  above. Operators who need GDPR-style erasure must use external
  tooling and accept that they are breaking the append-only model.
  A first-class privacy/erasure story is a candidate for
  `maybe-later.md` once we understand the deployment shape.
- **Verdict:** **tighter** (more append-only than Commanded).

### AGG-* — Aggregate execution

The SDK realises the load-execute-append loop. The store provides
the primitives; the SDK provides the orchestration.

#### AGG-001 — Hydration from snapshot + events

- **Commanded:** in-process state builder; reads snapshot, streams
  events from `snapshot_version + 1`, folds.
- **`instructed`:** identical algorithm, in the SDK. The SDK
  exposes a `load(aggregate_uuid, aggregate_module)` helper that
  calls `read_snapshot` (deferred to Pass 2) and `read_stream`,
  folds, returns `{state, version}`. No long-lived process; this
  runs per command (per D-0004).
- **Verdict:** **equivalent**.

#### AGG-002 — `apply/2` cannot fail

- **Commanded:** convention enforced by tests, not by the runtime.
- **`instructed`:** same convention; SDK documentation. The store
  is unaffected.
- **Verdict:** **equivalent**.

#### AGG-003 — Reject snapshot on version mismatch, fall back to full replay

- **Commanded:** the snapshotting module checks
  `metadata.snapshot_module_version` against the module's
  configured value.
- **`instructed`:** same. The SDK does the check; if mismatch,
  ignore the snapshot and replay from version 0. Cross-references
  SNAP-002 in Pass 2.
- **Verdict:** **equivalent**.

#### AGG-004 — In-memory aggregate cache *[BEAM-mechanism]*

- **Commanded:** GenServer holds hydrated state between commands.
- **`instructed`:** **dropped** per D-0004. Every command loads.
- **Verdict:** **looser on performance, equivalent on semantics**.
  Mitigation is the snapshot policy.

#### AGG-005, AGG-006 — Command function shape

- **Commanded:** typed return values fan-in to `{:ok, events} |
  {:error, reason}`.
- **`instructed`:** same shape, expressed in whatever the SDK
  language is. The store is uninvolved.
- **Verdict:** **equivalent**.

#### AGG-007 — Local fold agrees with persisted stream

- **Commanded:** the GenServer applies its own emitted events to
  its in-memory state before processing the next command.
- **`instructed`:** with no cache, "the next command" starts from a
  fresh load that reads the just-persisted events. The fold-and-
  persist agreement is automatic: the SDK never reuses its
  post-append in-memory state.
- **Verdict:** **equivalent, by a cheaper route**.

#### AGG-008 — `Commanded.Aggregate.Multi`

- **Commanded:** a builder that lets a command produce events in
  stages, each stage seeing the state of the previous one.
- **`instructed`:** an SDK helper, not a store concern. The store
  only sees the final flat list of events to append. The SDK can
  realise multi-stage construction by repeatedly applying staged
  events to a local copy of state.
- **Verdict:** **equivalent** (pure SDK feature).

#### AGG-009 — Append with `expected_version = aggregate_version`

- **Commanded:** the aggregate process passes its observed version
  to `append_to_stream`.
- **`instructed`:** same. The SDK's load helper returns the
  observed version; the SDK's append helper uses it as
  `expected_version`. INV-APPEND-013 enforces.
- **Verdict:** **equivalent**.

#### AGG-010 — Retry on `wrong_expected_version`

- **Commanded:** `ExecutionContext` retries up to
  `retry_attempts`, defaulting to 0.
- **`instructed`:** **same semantics, default raised to a small
  positive number (e.g. 3) for v1**. Rationale: without an
  in-memory cache, the "winning" thread for an integer
  expected_version is whichever thread hits the store first. The
  loser's retry is cheap (re-read events since its observed
  version, re-fold, re-run command, re-append) and almost always
  succeeds on the second try. A default of 0 makes the no-cache
  story look worse than it is.
- **Verdict:** **tighter on default ergonomics, equivalent on
  semantics**. Applications that need at-most-one-attempt
  semantics set `retry_attempts: 0` explicitly. Recording this as a
  deliberate departure; revisit during SDK design in Phase 8 if
  the default proves wrong.

#### AGG-011 — Per-aggregate command serialisation *[BEAM-mechanism]*

- **Commanded:** GenServer mailbox.
- **`instructed`:** per D-0005, **realised by optimistic-lock
  retry** rather than by any cross-process serialisation. The
  net SDK-visible behaviour: concurrent commands on the same
  aggregate are linearised by INV-APPEND-013, and AGG-010 makes
  the losing thread try again on the new state.
- **Verdict:** **looser on throughput under contention** (retries
  cost work), **equivalent on linearisability**.

#### AGG-020, AGG-021 — Causation/correlation propagation

- **Commanded:** `ExecutionContext` sets
  `causation_id = command_uuid` and
  `correlation_id = supplied or generated` on every event in the
  batch.
- **`instructed`:** SDK does the same. The store contract
  (INV-META-001) just stores and echoes; the SDK is responsible
  for the policy of "all events in this command share the
  same causation_id". This is the foundation that lets process
  managers (Pass 3) inherit causation from their triggering event
  cleanly.
- **Verdict:** **equivalent**.

#### AGG-025 — Self-subscription to own stream *[BEAM-mechanism]*

- **Commanded:** the aggregate GenServer subscribes to its own
  stream to absorb external writes.
- **`instructed`:** **dropped**. With no cache, there is no
  in-memory state to keep in sync. The next command reads the
  store and gets the truth.
- **Verdict:** **looser by mechanism elimination, equivalent on
  semantics**.

#### AGG-030 — `aggregate_lifespan` *[BEAM-mechanism]*

- **Commanded:** controls when the GenServer terminates.
- **`instructed`:** **dropped**. No process, nothing to terminate.
- **Verdict:** **dropped**, no semantic loss.
