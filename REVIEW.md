# CQRS/ES Feature Review: Instructed vs Commanded

> Generated by systematic comparison of the Instructed Gleam framework against the
> [Commanded](https://github.com/commanded/commanded) Elixir library.
>
> **Legend**: ✅ Equivalent | ⚠️ Present with gaps | ❌ Missing | 📝 Intentional design difference

---

## 1. Aggregates [⚠️]

### What Commanded Provides
- Aggregate is a module implementing `execute/2` and `apply/2` callbacks (behaviour)
- Aggregate state is an Elixir struct created via `defstruct`
- `execute/2` can return: single event, list of events, `{:ok, events}`, `:ok`/`nil`/`[]` (no-op), `{:error, reason}`, or `%Multi{}`
- `apply/2` must never fail — events are facts
- State is rebuilt via `AggregateStateBuilder.populate/1`: snapshot → batched event replay (1000 per batch)
- Aggregate runs as a GenServer with `restart: :temporary` (not restarted on crash)
- Init defers state loading via `handle_continue(:populate_aggregate_state)`
- Subscribes to its own stream to detect externally-appended events
- External events must arrive sequentially (`stream_version == aggregate_version + 1`) or process stops
- Telemetry emitted for populate and execute operations

### What Instructed Provides
- ✅ `Aggregate` record-of-functions with `execute`, `apply_event`, `empty_state` (`aggregate.gleam`)
- ✅ `execute` returns `Result(List(event), String)` — covers Ok/Error cases
- ✅ `apply_event` is infallible (returns `state`, not `Result`)
- ✅ State rebuilt via `populate_from_event_store` with snapshot support and batched reading (1000 default)
- ✅ Aggregate server runs as OTP Actor (`aggregate_server.gleam`)
- ✅ Self-subscription to aggregate stream for external events (`ExternalEvent` message)
- ✅ Gap detection on external events (reloads from store if version mismatch)
- ⚠️ `execute` return type is `Result(List(event), String)` — no support for returning single events, `%Multi{}` directly, or `:ok`/`nil` (Gleam's type system naturally handles this — `Ok([])` is the equivalent of no-op)
- 📝 Error type is `String` not arbitrary term — design choice for Gleam's type safety

### Gaps & Issues
- **LOW**: No bare event or `{:ok, single_event}` return from execute — Gleam's type system means `Ok([event])` is the canonical form. This is a design choice, not a gap.
- **LOW**: External event handling: on gap, Instructed reloads full state (`load_state`), while Commanded stops the process. Instructed's approach is more resilient but could mask bugs.
- **MEDIUM**: Commanded's `execute/2` can return `%Multi{}` directly — Instructed requires using `multi.to_result()` inside the execute function. Functionally equivalent but different ergonomics.

## 2. Command Routing & Dispatch [⚠️]

### What Commanded Provides
- Compile-time router with `identify` and `dispatch` macros (code generation)
- `identify` macro: `by:` (field name or function), `prefix:` (string or function)
- `dispatch` macro: maps command modules to handler/aggregate with options
- Compile-time duplicate command detection (raises `ArgumentError`)
- Identity extracted by `ExtractAggregateIdentity` middleware
- `Dispatcher` uses `Task.Supervisor.async_nolink` for isolation
- Dispatch options: `consistency`, `returning`, `timeout`, `retry_attempts`, `metadata`, `causation_id`, `correlation_id`
- `returning` supports: `false`, `:aggregate_state`, `:aggregate_version`, `:events`, `:execution_result`
- Default timeout: 5000ms, default retries: 10
- Separate handler module support (`to:` + `aggregate:`) with `handle/2` function
- Aggregate identity must be non-empty binary string

### What Instructed Provides
- ✅ Runtime router via `router.new()` with `identity` function (`router.gleam`)
- ✅ Identity prefix via `with_prefix` (string only, not function)
- ✅ Middleware support via `with_middleware`
- ✅ Dispatch timeout configurable via `with_dispatch_timeout` (default 5000ms)
- ✅ Retry attempts configurable via `with_retry_attempts` (default 10)
- ✅ `dispatch_with_context` supports causation_id, correlation_id, metadata
- ✅ Identity validation (rejects empty/whitespace-only)
- ✅ Registry actor manages aggregate server processes per stream_id
- ✅ Strong/eventual/selective consistency via pipeline and subscriptions
- ⚠️ `returning` option defined in `command_context.gleam` but **not wired into the router dispatch path** — `DispatchResult` always returns state, version, and events
- ❌ No compile-time command registration or duplicate detection (Gleam has no macros)
- ❌ No separate handler module support — aggregate IS the handler
- ❌ No `Task.Supervisor.async_nolink` isolation — commands execute directly via actor `process.call`
- 📝 Runtime configuration instead of compile-time macros — intentional Gleam design choice

### Gaps & Issues
- **MEDIUM**: `returning` option types exist in `command_context.gleam` (`ReturnNothing`, `ReturnAggregateState`, etc.) but the router always returns the full `DispatchResult`. The `CommandContext` type is not used by the router's dispatch path at all.
- **LOW**: No separate command handler modules — in Commanded, you can route commands to a handler module that delegates to an aggregate. Instructed's aggregate-as-handler pattern is simpler and type-safe.
- **MEDIUM**: No task isolation — if the aggregate server crashes during command execution, the calling process receives an error from `process.call` but there's no explicit `Task.Supervisor` wrapper. The actor model provides similar isolation since the caller and aggregate are separate processes.
- **LOW**: No compile-time duplicate command detection — must be caught at runtime via identity function logic.

## 3. Middleware Pipeline [✅]

### What Commanded Provides
- `Commanded.Middleware` behaviour with `before_dispatch/1`, `after_dispatch/1`, `after_failure/1`
- `Pipeline` struct with: command, command_uuid, causation_id, correlation_id, metadata, assigns, halted, response, consistency, identity, identity_prefix
- `assign/3`, `assign_metadata/3` for adding data
- `halt/1` stops `before_dispatch` and `after_dispatch` chains; `after_failure` always runs all middleware
- Built-in: `ExtractAggregateIdentity`, `ConsistencyGuarantee`, `Logger`
- Middleware applied left-to-right; user middleware prepended before defaults

### What Instructed Provides
- ✅ `Middleware` record with `before_dispatch`, `after_dispatch`, `after_failure` (`middleware.gleam`)
- ✅ `Pipeline` type with command, command_id, causation_id, correlation_id, metadata, assigns, halted, response, consistency, identity, identity_prefix
- ✅ `assign/3`, `assign_metadata/3` functions
- ✅ `halt/1` stops before/after_dispatch chains; `after_failure` always runs all
- ✅ `run_before_dispatch`, `run_after_dispatch`, `run_after_failure` with correct halting semantics
- ✅ `Consistency` type with `Eventual`, `Strong`, `Selective(handlers)` variants
- ⚠️ No built-in `ExtractAggregateIdentity` middleware — identity extraction is done directly in router
- ⚠️ No built-in `Logger` middleware — users must create their own
- 📝 Assigns use `Dict(String, String)` instead of `%{atom => any}` — Gleam type safety tradeoff

### Gaps & Issues
- **LOW**: No built-in logging middleware — easy for users to create
- **LOW**: Identity extraction built into router rather than as middleware — functionally equivalent, just a different architectural choice
- **LOW**: Assigns are `Dict(String, String)` — can't store arbitrary values. In practice, middleware assigns are typically strings anyway.

## 4. Event Handlers [⚠️]

### What Commanded Provides
- GenServer process with trap_exit, monitored subscription
- Configuration: name, consistency, start_from, subscribe_to, concurrency, batch_size, state
- Singleton guarantee via event store subscription (advisory locks in PostgreSQL)
- `handle/2` callback receives `(event, metadata_map)` — returns `:ok`, `{:ok, new_state}`, `{:error, reason}`, `{:error, :already_seen_event}`
- Default catch-all `handle/2` generated at compile time (ignores unknown events)
- Error chain: `error/3` callback → app-level `on_event_handler_error` config → built-in strategies
- `FailureContext` struct with context, handler_state, metadata, stacktrace
- Exponential backoff strategy built-in (failures² × 1000 + jitter, clamped 1s–24h)
- Handler state in metadata under `:state` key
- Subscription backoff on connection failure (1s–60s via `:backoff` library)
- `reset` message to delete subscription and replay from scratch
- `after_start/1` callback after subscription confirmed
- Telemetry events for handle start/stop/exception

### What Instructed Provides
- ✅ Actor-based event handler (`event_handler.gleam`)
- ✅ Configuration: name, handle_event, initial_state, stream_id, start_from, consistency, on_error, upcaster
- ✅ `handle_event` callback receives `(event, RecordedEvent, handler_state)` — returns `Result(handler_state, String)`
- ✅ Error callback with `Retry`, `RetryWithDelay`, `Skip`, `Stop` strategies
- ✅ `last_seen_event` idempotency guard (Invariant 20)
- ✅ Persistent subscription with ack-based backpressure
- ✅ `start_from` only applies on first subscription creation
- ✅ Strong consistency acking via subscriptions actor
- ✅ Telemetry instrumentation (start/stop/exception)
- ✅ Exponential backoff helper (`error.backoff` and `error.backoff_with_jitter`)
- ⚠️ No `{:error, :already_seen_event}` return handling — only `Result(state, String)`
- ⚠️ Subscription failure on start: deletes and recreates subscription (loses position in in-memory adapter)
- ❌ No `concurrency` option (single handler instance only)
- ❌ No `batch_size` / `handle_batch` support
- ❌ No `reset` mechanism for replaying events
- ❌ No `after_start` callback
- ❌ No `init/1` callback for runtime configuration
- ❌ No app-level `on_event_handler_error` fallback config
- ❌ Handler state is not injected into metadata
- ❌ No subscription backoff on connection failure (immediate retry or fail)

### Gaps & Issues
- **HIGH**: Subscription recreation on `SubscriptionAlreadyExists` error (`event_handler.gleam` start function) deletes and recreates the subscription. For the in-memory adapter, this loses the subscription position, causing full event replay on every handler restart. The PostgreSQL adapter preserves position via database, mitigating this for production.
- **MEDIUM**: No `concurrency` support — all events processed by a single handler instance. Limits throughput for high-volume event processing.
- **MEDIUM**: No `batch_size` / `handle_batch` — no way to process events in batches for efficiency.
- **MEDIUM**: No `reset` mechanism — can't trigger a full replay/rebuild of a read model without manual subscription deletion.
- **LOW**: No `after_start` callback — minor convenience feature.
- **LOW**: No app-level error handler config — each handler must configure its own `on_error`.

## 5. Projections [⚠️]

### What Commanded Provides
- Projections are event handlers — no separate core module
- `commanded_ecto_projections` library provides database-backed projections with Ecto.Multi
- `project` macro generates handler clauses
- `before_reset/0` callback for cleaning read model before replay
- Strong consistency support for POST/Redirect/GET pattern
- Ecto.Multi transactional projection updates

### What Instructed Provides
- ✅ Dedicated `projection.gleam` module — actor-based, builds on event handler pattern
- ✅ In-memory state queryable via `get_state/2` (synchronous call)
- ✅ Idempotency via `last_seen_event` guard
- ✅ Error handling via `on_error` callback (same strategies as event handler)
- ✅ `start_from` semantics matching Commanded
- ✅ Strong consistency support via subscriptions actor (`with_consistency`)
- ⚠️ In-memory only — no database-backed projection support in core
- ❌ No `before_reset` / reset mechanism
- ❌ No Ecto.Multi or transactional update support (Gleam ecosystem difference)

### Gaps & Issues
- **MEDIUM**: Projections are in-memory only. Production use requires either:
  1. Using an event handler with database calls inside `handle_event`
  2. Building a custom database-backed projection module
  This is partially mitigated by the fact that any event handler can act as a projector.
- **LOW**: No reset/rebuild mechanism — same gap as event handlers.
- 📝 No Ecto equivalent in Gleam ecosystem — this is an ecosystem gap, not a framework gap.

## 6. Process Managers [⚠️]

### What Commanded Provides
- Three-layer hierarchy: ProcessRouter → DynamicSupervisor → ProcessManagerInstance
- `interested?/1,2` routing: `{:start, uuid}`, `{:start!, uuid}`, `{:continue, uuid}`, `{:continue!, uuid}`, `{:stop, uuid}`, `false`
- Multi-instance fan-out: uuid can be a list
- `handle/2,3` returns commands or `{:error, reason}`
- `apply/2,3` mutates state after successful command dispatch
- `after_command/2,3` can stop instance after specific command
- `error/3` with separate handling for event errors vs command dispatch errors
- Command dispatch errors have `pending_commands` in FailureContext
- Command error strategies: retry, skip (continue/discard pending), continue (replace commands), stop
- State persisted as snapshot after each event (source_version = event_number)
- Snapshot loaded on startup for state and idempotency (last_seen_event)
- Snapshot deleted on stop
- Causation chain: commands dispatched with causation_id=event_id, correlation_id=event's correlation_id
- Event timeout (stops router if instance doesn't ack in time)
- Idle timeout (stops instance after inactivity)
- Per-instance processes for parallelism
- Strict routing validation (start!/continue!)

### What Instructed Provides
- ✅ Single actor managing all instances in a Dict (`process_manager.gleam`)
- ✅ `Interest` type: `Start`, `StartStrict`, `StartMany`, `Continue`, `ContinueStrict`, `ContinueMany`, `Stop`, `StopMany`, `Skip`
- ✅ `handle` callback returns `Result(List(command), String)`
- ✅ `apply_event` mutates state after command dispatch
- ✅ `after_command` callback with `AfterContinue`/`AfterStop`
- ✅ Separate `on_event_error` and `on_command_error` callbacks
- ✅ Command error strategies: `CmdRetry`, `CmdRetryWithDelay`, `CmdSkip`, `CmdDiscardPending`, `CmdContinueWith`, `CmdStop`
- ✅ State persisted as snapshot after each event (source_version = event_number)
- ✅ Snapshot loaded on startup (get_or_load_instance)
- ✅ Snapshot deleted on stop
- ✅ Causation chain propagation (causation_id = event_id, correlation_id = event's correlation_id)
- ✅ Per-instance idempotency via last_seen_event from snapshot
- ✅ Strict routing validation with snapshot store checking
- ✅ Strong consistency acking via subscriptions actor
- ⚠️ All instances in single actor — no per-instance parallelism
- ❌ No event timeout (no mechanism to detect hung instances)
- ❌ No idle timeout for instances
- ❌ `interested?` doesn't receive metadata (only event data) — no `/2` variant
- ❌ No `identity/0` function to get process UUID within callbacks

### Gaps & Issues
- **MEDIUM**: Single-actor architecture means all PM instances are serialized through one mailbox. This prevents parallel event processing across instances. For high-throughput systems, this is a bottleneck. However, it simplifies state management and eliminates many concurrency issues.
- **MEDIUM**: No event timeout — if command dispatch hangs, the PM actor blocks indefinitely, preventing other instances from processing events.
- **LOW**: No idle timeout for instances — instances stay in memory even when unused. Memory could grow unbounded for PMs with many instances.
- **LOW**: `interested?` doesn't receive metadata — can't make routing decisions based on causation_id, correlation_id, etc.

## 7. Snapshots [✅]

### What Commanded Provides
- `SnapshotData` struct: source_uuid, source_version, source_type, data, metadata, created_at
- Configuration: `snapshot_every: N`, `snapshot_version: N`
- Version validation: reads `metadata["snapshot_module_version"]` — ignores outdated snapshots
- Aggregate snapshots: configurable frequency, async via `send(self(), {:take_snapshot, ...})`
- PM snapshots: after every event, source_version = event_number
- Serialization through configured serializer (JSON default)
- Snapshot deleted on PM stop

### What Instructed Provides
- ✅ `SnapshotData` type: source_uuid, source_version, source_type, data, created_at (`snapshot.gleam`)
- ✅ `SnapshotConfig` with `snapshot_every` and `snapshot_version`
- ✅ Version validation via `encode_snapshot_type`/`decode_snapshot_version` (encodes version in source_type string)
- ✅ Aggregate snapshots taken in `maybe_take_snapshot` when threshold reached
- ✅ PM snapshots after every event with event_number as source_version
- ✅ PM snapshots deleted on stop
- ✅ `snapshot.coerce` for type-safe bridging between state and event type parameters
- ⚠️ Aggregate snapshot is synchronous (not async via message) — blocks command reply briefly
- ⚠️ Version encoded in source_type string ("aggregate:v1") rather than metadata map

### Gaps & Issues
- **LOW**: Synchronous snapshot taking in aggregate server — Commanded defers via async message to avoid blocking the command reply. In practice, snapshot writes are fast (especially in-memory), so this is a minor performance difference.
- **LOW**: Version encoding differs (source_type string vs metadata map) — functionally equivalent, just different encoding.

## 8. Event Store Interface [✅]

### What Commanded Provides
- `EventStore.Adapter` behaviour with callbacks: append_to_stream, stream_forward, subscribe, subscribe_to, ack_event, unsubscribe, delete_subscription, read_snapshot, record_snapshot, delete_snapshot
- `expected_version` semantics: `:any_version`, `:no_stream`, `:stream_exists`, integer
- Transient subscriptions (fire-and-forget messages to PID)
- Persistent subscriptions with durable position, ack-based backpressure
- `stream_forward` returns lazy `Stream` (Elixir enumerable)
- In-memory adapter with full OCC, serialization support, persistent subscription with concurrency
- Adapter meta pattern for adapter-specific state

### What Instructed Provides
- ✅ `EventStore` record-of-functions with all equivalent operations (`event_store.gleam`)
- ✅ `ExpectedVersion`: `AnyVersion`, `NoStream`, `StreamExists`, `ExactVersion(Int)`
- ✅ Transient subscriptions via callback functions
- ✅ Persistent subscriptions with durable position and ack-based backpressure
- ✅ In-memory adapter (`in_memory_event_store.gleam`) with full OCC
- ✅ SQLite adapter (`instructed_sqlite.gleam`) with schema creation, persistent subscriptions
- ✅ PostgreSQL adapter (`instructed_postgres.gleam`) with transactional OCC, poll-based persistent subscriptions, gap detection
- ✅ `read_all_forward` and `get_latest_event_number` operations (not in Commanded's core adapter interface)
- ⚠️ `read_stream_forward` returns `Result(List, Error)` not lazy stream — loads all events into memory at once (batched by caller)
- ⚠️ No `concurrency_limit` or `partition_by` on persistent subscriptions
- 📝 Record-of-functions instead of behaviour — idiomatic Gleam pattern

### Gaps & Issues
- **MEDIUM**: No lazy stream for event reading — for aggregates with millions of events, the batched approach works but each batch is fully loaded into memory. Commanded's lazy `Stream` is more memory-efficient for very large streams.
- **MEDIUM**: No `concurrency_limit` or `partition_by` on subscriptions — limits subscription concurrency patterns.
- **LOW**: PostgreSQL adapter has sophisticated gap detection for BIGSERIAL out-of-order commits — a well-engineered solution.

## 9. Optimistic Concurrency Control [✅]

### What Commanded Provides
- `expected_version` on `append_to_stream`: `:any_version`, `:no_stream`, `:stream_exists`, integer
- On `:wrong_expected_version`: aggregate rebuilds state from events and retries
- Default 10 retry attempts
- Retry at two levels: aggregate level (version conflict) and dispatcher level (process exit)

### What Instructed Provides
- ✅ `ExpectedVersion` type: `AnyVersion`, `NoStream`, `StreamExists`, `ExactVersion(Int)`
- ✅ Version conflict triggers `rebuild_from_current_version` (incremental, not full replay) and retry
- ✅ Default 10 retry attempts (`default_retry_attempts = 10`)
- ✅ `TooManyAttempts` error after exhaustion
- ✅ In-memory adapter implements full OCC with specific error types
- ✅ PostgreSQL adapter uses transactional append with UNIQUE constraint violation → VersionConflict
- ✅ SQLite adapter uses UNIQUE constraint on (stream_id, stream_version)

### Gaps & Issues
- **None significant**. OCC is well-implemented across all three adapters. The incremental rebuild (`rebuild_from_version`) is actually more efficient than Commanded's full `rebuild_from_events` in the retry path.

## 10. Command Serialization per Aggregate [✅]

### What Commanded Provides
- Each aggregate instance is a GenServer — commands serialized via mailbox
- Commands to different aggregates run in parallel (different processes)
- `DynamicSupervisor` + `Registration` manage aggregate processes

### What Instructed Provides
- ✅ Each aggregate instance has its own Actor — commands serialized via `process.call`
- ✅ Different aggregates run in parallel (separate actors)
- ✅ Registry actor manages aggregate server processes per stream_id
- ⚠️ Registry is a simple Dict-based actor, not a `DynamicSupervisor`
- ⚠️ No detection of dead aggregate servers — if an aggregate actor crashes, the registry still holds a stale reference

### Gaps & Issues
- **MEDIUM**: Registry doesn't detect dead aggregate servers. If an aggregate actor crashes (e.g., from an unhandled error), the registry retains the dead Subject. Subsequent dispatches would fail with a timeout rather than starting a new aggregate. Commanded handles this because `DynamicSupervisor` tracks child lifecycle and `Registration` deregisters on process exit.

## 11. Event Ordering [✅]

### What Commanded Provides
- Global event ordering via `event_number` (monotonically increasing across all streams)
- Per-stream ordering via `stream_version` (sequential within stream)
- Handlers receive events in `event_number` order (via subscription)
- Subscription callback delivers events sequentially

### What Instructed Provides
- ✅ Global `event_number` (monotonically increasing) in all adapters
- ✅ Per-stream `stream_version` (sequential within stream)
- ✅ Persistent subscriptions deliver events in event_number order
- ✅ Ack-based backpressure ensures sequential processing
- ✅ PostgreSQL adapter handles BIGSERIAL gaps with contiguous-prefix detection and gap retry

### Gaps & Issues
- **None significant**. Event ordering is correctly maintained across all adapters.

## 12. Strong vs Eventual Consistency [✅]

### What Commanded Provides
- `consistency: :strong` on dispatch blocks until all strong handlers ack
- `consistency: :eventual` returns immediately (default)
- Selective: `consistency: [ModuleName, "handler_name"]`
- `ConsistencyGuarantee` middleware calls `Subscriptions.wait_for`
- PubSub-based ack distribution (works across nodes with PhoenixPubSub)
- Dispatcher PID excluded from wait (prevents deadlock when handler dispatches)
- Timeout: 5000ms default → `{:error, :consistency_timeout}`
- ETS-based ack tracking with TTL purging (1 hour)

### What Instructed Provides
- ✅ `Consistency` type: `Eventual`, `Strong`, `Selective(handlers)`
- ✅ `subscriptions.gleam` actor tracks handler registrations and acked versions
- ✅ `wait_for` and `wait_for_handlers` with timeout
- ✅ Automatic PID-based exclusion of dispatching handler (`register_pid`, `caller_pid`)
- ✅ `ConsistencyTimeout` error on timeout
- ✅ TTL-based purging of stale acks (1 hour, matching Commanded)
- ✅ Periodic purge scheduling (every 5 minutes)
- ✅ Router integrates wait_for in `dispatch_through_server`
- ⚠️ No PubSub system — single-node only for ack distribution

### Gaps & Issues
- **MEDIUM**: No PubSub adapter system — ack events are tracked in a single subscriptions actor. In a multi-node deployment, handlers on different nodes can't participate in consistency tracking. Commanded supports this via PhoenixPubSub with PG2 or Redis.
- **LOW**: Single subscriptions actor could be a bottleneck under very high throughput, but for most use cases it's fine.

## 13. Error Handling & Retry Strategies [⚠️]

### What Commanded Provides
- Event handler `error/3` callback with `FailureContext` (context, handler_state, metadata, stacktrace, pending_commands)
- Strategies: `{:retry, context}`, `{:retry, delay, context}`, `:skip`, `{:stop, reason}`
- App-level `on_event_handler_error`: `:stop` | `:backoff` | module
- Built-in `ErrorHandler.backoff/3`: failures² × 1000 + jitter (1s–24h)
- PM error/3 with separate handling for event vs command errors
- PM command errors: retry, skip+continue_pending, skip+discard_pending, continue(new_commands), stop
- `FailureContext` includes `pending_commands` for command dispatch failures
- Timer.sleep blocks GenServer during retry delay
- Retry is recursive — if retry fails, error/3 is called again

### What Instructed Provides
- ✅ `ErrorAction` type: `Retry(context)`, `RetryWithDelay(delay_ms, context)`, `Skip`, `Stop(reason)`
- ✅ `PMCommandErrorAction` type: `CmdRetry`, `CmdRetryWithDelay`, `CmdSkip`, `CmdDiscardPending`, `CmdContinueWith`, `CmdStop`
- ✅ `FailureContext` type with context, handler_state, failure_count, last_error, stacktrace
- ✅ `backoff` and `backoff_with_jitter` helper functions (matching Commanded's formula)
- ✅ Event handler retry is recursive (handle_error calls itself)
- ✅ `process.sleep` for delay-based retry (blocks actor, matching Commanded)
- ✅ PM has separate `on_event_error` and `on_command_error` callbacks
- ⚠️ `FailureContext` doesn't include `pending_commands` for PM command errors — pending commands are passed directly to `on_command_error` callback as a parameter
- ❌ No app-level `on_event_handler_error` fallback config
- ❌ PM default event error behavior is skip (not stop) — differs from Commanded's default stop

### Gaps & Issues
- **MEDIUM**: PM default event error behavior (`on_event_error: None`) skips the event silently (`handle_event_error` returns `state` unchanged). Commanded defaults to stopping. This means PM event handling errors are silently swallowed in Instructed, which could lead to data loss.
- **LOW**: No app-level error handler config — each handler/PM must configure its own error callback.

## 14. Causation & Correlation ID Tracking [✅]

### What Commanded Provides
- Command dispatch generates command_id (UUID)
- command_id becomes causation_id on produced events
- correlation_id propagated from dispatch options to events
- PM dispatches commands with: causation_id = event_id, correlation_id = event's correlation_id
- Full causal chain: Command A → Event A → PM → Command B → Event B

### What Instructed Provides
- ✅ Router generates command_id and correlation_id (UUIDs) in `dispatch`
- ✅ causation_id/correlation_id passed through to `EventData` in `execute_once`
- ✅ PM dispatches with causation_id = event_id, correlation_id = event's correlation_id (`dispatch_commands`)
- ✅ `dispatch_with_context` allows explicit causation/correlation IDs
- ✅ Full causal chain preserved through PM command dispatch

### Gaps & Issues
- **None significant**. Causation and correlation chain propagation is correctly implemented.

## 15. Idempotency [✅]

### What Commanded Provides
- Event handler: `last_seen_event` (in-memory) skips already-processed events
- PM: `last_seen_event` from snapshot's source_version
- Persistent subscription position: events re-delivered from last ack on restart
- `{:error, :already_seen_event}` return from handler treated as success
- PM instances: idempotency check at both router and instance level

### What Instructed Provides
- ✅ Event handler: `last_seen_event` guard in `handle_actor_message`
- ✅ Projection: `last_seen_event` guard in `handle_projection_message`
- ✅ PM: per-instance `last_seen_event` from snapshot's source_version
- ✅ Persistent subscription position tracking via ack_event
- ⚠️ No `{:error, :already_seen_event}` special return — handler errors always go through error callback

### Gaps & Issues
- **LOW**: No `already_seen_event` special return value. Users must implement their own idempotency checks in handler logic if needed beyond the `last_seen_event` guard. The built-in guard covers the primary case (subscription-level idempotency).

## 16. Multi Module [✅]

### What Commanded Provides
- `Multi.new(aggregate)` → `%Multi{}`
- `Multi.execute(multi, step_name \\ false, fun)` — named steps, arity-1 or arity-2 (with steps map)
- `Multi.reduce(multi, step_name, enumerable, fun)` — arity-2 or arity-3
- `Multi.run(multi)` → `{aggregate, events}` or `{:error, reason}`
- Named steps allow later functions to access intermediate states
- Nested Multi support (recursive `run`)
- Atomic: error discards all events
- Integrated into aggregate `execute_command` — `%Multi{}` return triggers `Multi.run`

### What Instructed Provides
- ✅ `multi.new(state)` creates Multi chain (`multi.gleam`)
- ✅ `multi.execute(multi, fn(state) -> Result(List(event), String))` — execute stage
- ✅ `multi.apply(multi, apply_fn)` — apply accumulated events to state between stages
- ✅ `multi.reduce(multi, items, execute_fn, apply_fn)` — iterate over list
- ✅ `multi.to_result()` → `Result(List(event), String)` — collapses chain
- ✅ Atomic: error discards all events
- ✅ `get_state`, `get_events`, `has_error` inspection functions
- ❌ No named steps — can't access intermediate states by name
- ❌ No nested Multi support — execute functions must return `Result(List(event), String)`, not `Multi`
- ❌ No arity-2 execute functions (receiving steps map)
- 📝 Explicit `apply` call between stages vs Commanded's automatic application — design choice for explicitness

### Gaps & Issues
- **LOW**: No named steps or arity-2 execute functions — advanced feature rarely used in practice
- **LOW**: No nested Multi — can be worked around by chaining more execute/apply calls
- 📝 Instructed's explicit `apply` between stages is actually clearer than Commanded's automatic application, where state evolution is implicit

## 17. Aggregate Lifespan Management [✅]

### What Commanded Provides
- `AggregateLifespan` behaviour: `after_event/1`, `after_command/1`, `after_error/1`
- Return values: timeout (integer), `:infinity`, `:hibernate`, `:stop`, `{:stop, reason}`
- `DefaultLifespan`: `:infinity` for events/commands, `{:stop, error}` for exceptions
- `after_event` called with LAST event only
- `after_command` called when command produces NO events
- Lifespan timeout integrated with GenServer timeout mechanism
- Snapshot taken before lifespan timeout applied (deferred via async message)

### What Instructed Provides
- ✅ `Lifespan` record: `after_command`, `after_error`, `after_event` callbacks (`lifespan.gleam`)
- ✅ `LifespanDecision`: `KeepRunning`, `Stop`, `StopAfter(ms)`, `Hibernate` (falls back to KeepRunning)
- ✅ `always_running()`, `new_idle(ms)`, `stop_after_command()` convenience constructors
- ✅ `after_command` called after successful command (receives state and command)
- ✅ `after_error` called after command error (receives state, command, reason)
- ✅ `after_event` called after external event applied
- ✅ `StopAfter(ms)` implemented via `process.send_after` with timer cancellation
- ⚠️ `after_command` receives `(state, command)` — Commanded passes only command
- ⚠️ `after_event` receives `(state, event)` — Commanded passes only event (last one)
- 📝 Hibernate falls back to KeepRunning — Gleam actors don't support Erlang-level hibernation

### Gaps & Issues
- **None significant**. The lifespan implementation is comprehensive and functionally equivalent. Instructed's callbacks receive more context (state + event/command) which is actually more useful than Commanded's event/command-only approach.

## 19. Application Supervision Tree [⚠️]

### What Commanded Provides
- Application is an OTP Supervisor module (named, starts all infrastructure)
- Full supervision tree: EventStore adapters → PubSub → Registry → TaskSupervisor → Aggregates.Supervisor → Subscriptions.Registry → Subscriptions
- `start_link/1` with runtime config, `init/1` callback for dynamic config
- Named applications for multi-tenancy
- Child process namespacing via `Module.concat`
- Config priority: compile-time → app env → start_link opts → init/1

### What Instructed Provides
- ✅ `Application` struct grouping event store, router, and subscriptions (`application.gleam`)
- ✅ `start` returns Application struct — not a supervisor
- ✅ Component start helpers: `start_event_handler`, `start_projection`, `start_process_manager`
- ✅ Subscriptions actor auto-injection into router and components
- ✅ Multi-tenancy via separate Application instances with separate event stores
- ⚠️ Application is a plain struct, not a supervisor — no automatic component lifecycle management
- ❌ No supervision tree — user must supervise components manually
- ❌ No `init/1` callback for dynamic configuration
- ❌ No automatic restart of failed components

### Gaps & Issues
- **HIGH**: No supervision tree. If an event handler, projection, or process manager crashes, it's gone. Users must manually set up `static_supervisor` trees and wire in component restarts. Commanded handles this automatically. This is a significant production-readiness gap.
- **MEDIUM**: No component lifecycle management. The Application doesn't track started components or provide a way to stop/restart them.
- 📝 The documentation shows how to use `gleam/otp/static_supervisor` manually, which mitigates this gap.

## 22. Batch Processing & Concurrency in Handlers [❌]

### What Commanded Provides
- `batch_size: N` enables batch mode — `handle_batch/1` receives list of `{event, metadata}`
- `concurrency: N` starts N handler instances with optional `partition_by` function
- Events partitioned via `erlang.phash2(key, N)` for deterministic routing
- Batch and concurrency are mutually exclusive
- Strong consistency incompatible with concurrency > 1
- Multiple subscribers per persistent subscription with in-flight tracking

### What Instructed Provides
- ❌ No `batch_size` or `handle_batch` support
- ❌ No `concurrency` option for handlers
- ❌ No `partition_by` function
- ❌ No multi-subscriber persistent subscriptions

### Gaps & Issues
- **MEDIUM**: No batch processing — high-volume handlers must process events one at a time. This limits throughput for I/O-bound handlers (e.g., database writes that could be batched).
- **MEDIUM**: No handler concurrency — single handler instance processes all events sequentially. For CPU-bound or I/O-bound handlers, this limits throughput.
- **LOW**: No partitioning — can't ensure related events are processed by the same handler instance.

## Critical Issues for Production Use

1. **No supervision tree** (Area 19, HIGH): Crashed components are not automatically restarted. Users must build their own supervision trees. This is the single biggest gap for production readiness.

2. **Subscription recreation loses position** (Area 4, HIGH): Event handler restart deletes and recreates subscriptions in the in-memory adapter, causing full replay. The PostgreSQL adapter mitigates this. The SQLite adapter has the same issue since persistent subscriptions also use in-process tracking.

3. **Dead aggregate server references in registry** (Area 10, MEDIUM): Registry doesn't detect or clean up dead aggregate actors. Stale references cause dispatch timeouts instead of starting fresh aggregates.

4. **PM event error default is skip, not stop** (Area 13, MEDIUM): Process manager silently skips event handling errors when no `on_event_error` is configured, potentially losing events. Commanded defaults to stopping.

5. **No PubSub for multi-node** (Area 12, MEDIUM): Strong consistency tracking is single-node only. Multi-node deployments can't use strong consistency guarantees.

6. **Single-actor PM bottleneck** (Area 6, MEDIUM): All PM instances share one actor, preventing parallel event processing.

---

## Recommended Priority Order

1. **Add supervision integration** — Provide a helper to build a supervision tree from an Application config, auto-restarting event handlers, projections, and process managers.

2. **Fix registry lifecycle** — Monitor aggregate server actors and remove dead references from the registry. Consider using `gleam_otp`'s `factory_supervisor` pattern.

3. **Change PM default error behavior** — Default `on_event_error: None` should stop the PM (matching Commanded), not silently skip errors.

4. **Fix subscription recreation** — On `SubscriptionAlreadyExists`, re-register the handler callback with the existing subscription instead of deleting and recreating.

5. **Add handler concurrency** — Support `concurrency: N` for event handlers and projections to improve throughput.

6. **Add batch processing** — Support `batch_size` and `handle_batch` for efficient bulk event processing.

7. **Add handler reset mechanism** — Allow deleting subscription and replaying from a configured start position.

8. **Add PubSub adapter system** — Enable multi-node strong consistency tracking.

9. **Wire `returning` option** — Connect the `CommandContext.Returning` type to the router dispatch path so callers can control what's returned.

10. **Add event timeout to PM** — Detect hung PM instances that don't ack events within a configurable timeout.
